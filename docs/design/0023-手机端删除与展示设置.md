# 0023 手机端删除交互与展示设置

- 状态：已实现（M13，2026-10-07；JVM 单测与真机联调通过，自定义背景图上传的真机验收待用户执行）
- 对应阶段：Phase 5（M13）
- 关联：`docs/design/0020-手机客户端编辑.md`、`docs/design/0002-局域网配对与同步.md`、`docs/design/0001-菜单数据模型与接口契约.md`、`docs/design/0007-展示页背景图片.md`、`docs/design/0009-展示页内置背景样式.md`、`docs/architecture.md`

## 1. 背景与目标

手机端已经能增删改菜单（M11），但实际用起来有两处不合手：

1. **删除入口用不了**：删除菜品要先点行 → 进编辑弹窗 → 找到「删除菜品」；删除分类只挂在**长按**分类 chip 上，而 MIUI 等系统下长按注入 / 手势冲突严重（`docs/design/0019` 第 8 节已记录过该问题），实际等于没有入口。
2. **展示设置只能在平板上改**：背景样式、自定义背景图、蒙版透明度、卡片透明度、是否有货提示目前只有平板管理页能改；手机端 `/state` 不下发这些字段，也没有对应写接口，摊主想在手机上调一下背景得跑到平板前。

目标：

1. 手机端管理模式下，**分类与菜品都能一键删除**，且都有二次确认，不依赖长按。
2. 手机端能改展示设置并**即时同步**到平板展示页：内置背景样式、自定义背景图（含上传）、蒙版透明度、卡片透明度、是否有货提示。

## 2. 方案设计（含取舍）

### 2.1 删除交互：行内显式按钮 + 二次确认

- 分类：管理模式下每个分类 chip 右侧显示「×」，点击弹二次确认后删除；**保留长按**作为次要入口（平板习惯），但不再是唯一入口。
- 菜品：管理模式下每行操作区在「卖出 / 撤销 / 沽清」之后补「删除」，点击弹二次确认后删除。
- 取舍：不用左滑删除——发现在差，且与系统返回手势冲突；不用长按弹菜单——同一手势已经证明不可靠。二次确认文案与平板管理页保持一致（`ui/dialogs/MenuDialogs.kt` 的确认弹窗复用）。
- 删除分类沿用现有语义：其下菜品级联软删除（`enabled = false`），历史 `SaleRecord` 保留。

### 2.2 展示设置同步：新增 `DisplaySettingsDto` + `PATCH /display` + `display.updated`

- 新增契约对象 `DisplaySettingsDto`：
  `backgroundStyleId`、`backgroundImagePath`、`backgroundScrimPercent`、`cardAlphaPercent`、`showStockHint`。
- `GET /state` 增加 `display` 字段，配对后客户端立即拿到当前展示设置。
- 新增 `PATCH /display`：只提交要改的字段（其余为 null 表示不改），主机落盘后广播 `display.updated`。
- **`backgroundImagePath` 采用三态**（与 `DishPatchRequest.imagePath` 一致）：`null` 不改、空串清除自定义背景图、非空设为该图；设置为非空时主机同时把 `backgroundStyleId` 置空（两者互斥，`0009` 既有约定）。
- 展示设置与菜单数据无关，**不 bump 全局 `version`**；`display.updated` 帧沿用当前 `version` 仅为满足报文字段统一。客户端不复用「版本前进」判据，改为直接比对设置内容。

### 2.3 自定义背景图上传（手机 → 平板）

- 复用现有 multipart 上传端点，新增查询参数区分规格：`POST /images?kind=background`。
  - 默认（无参数）：菜品图规格（长边 1280、JPEG 80），行为不变。
  - `kind=background`：背景图规格（长边 2048、JPEG 85），与平板相册导入完全一致。
- 上传成功后客户端再发 `PATCH /display {backgroundImagePath: <路径>}`，主机清除内置样式并广播。
- 取舍：不新开上传路径（复用 multipart 解析、大小校验与魔数判型），也不用「无损 PNG」——手机上传的是相册照片，JPEG 85 与平板现状一致且体积更小。

### 2.4 权限与一致性

- 展示设置的写操作与背景图上传**同样受「允许手机编辑」开关约束**：关闭时主机返回 403 `forbidden`，与菜单写操作一致，方便摊主一键收回手机的全部能力。
- 手机端提交采用既有语义：**提交即禁用 + 等广播对齐**，失败提示主机中文 message，不做乐观更新与回滚。
- 手机端在设置弹窗内提供本地即时预览（背景样式 / 透明度直接改本地状态），`display.updated` 到达后以主机值为准。

## 3. 接口与数据模型变化

- `net/protocol/Contract.kt`：
  - 新增 `DisplaySettingsDto(backgroundStyleId, backgroundImagePath, backgroundScrimPercent, cardAlphaPercent, showStockHint)`。
  - 新增 `DisplayPatchRequest`（各字段可空 = 不改；`backgroundImagePath` 三态）。
  - `StateDto` 增加 `display: DisplaySettingsDto? = null`（老客户端忽略）。
  - `EventType` 增加 `DISPLAY_UPDATED = "display.updated"`。
- `host/HostMessages.kt`：`MenuBackend` 增加 `display()` 与 `applyDisplay(patch)`；`RepositoryMenuBackend` 落地到 `SettingsStore` 并构造 `DisplaySettingsDto`。
- `host/HostApi.kt`：新增路由 `PATCH /display`（写方法，受编辑开关判定）；`handleImageUpload` 增加 `kind` 参数分派规格。
- `host/WsHub.kt`：新增 `displayEvent(settings, version)`。
- `host/HostServer.kt`：`/images` 解析 `kind` 查询参数；`PATCH /display` 成功后广播 `display.updated`。
- `imaging/ImageStore.kt`：新增 `importBackgroundFromBytes(bytes)`（长边 2048、JPEG 85）。
- 客户端：`ClientMirror` 保存并应用 `display`；`ClientSession.updateDisplay()`；`HostRestClient.updateDisplay()` / `uploadImage(kind)`；`ClientCommand` 增加 `UpdateDisplay` 命令。

## 4. 边界与失败场景

| 场景 | 行为 |
| --- | --- |
| 手机删除分类 | 二次确认后提交；该分类下菜品随之从两端列表消失 |
| 手机删除菜品 | 二次确认后提交；菜品图由主机侧删除 |
| 平板关闭「允许手机编辑」 | 删除按钮与展示设置控件全部禁用；强行提交返回 403 并提示 |
| 手机离线 | 管理入口不可用；展示设置控件禁用 |
| 上传背景图过大 / 非图片 | 主机返回 413 / 400 与中文提示，设置不变 |
| 背景图与内置样式互斥 | 选内置样式清除自定义图；上传自定义图清除样式 id |
| 平板同时改设置 | 以 `display.updated` 最后一次广播为准，两端对齐 |
| 老客户端（无 `display` 字段） | 解析不受影响（`display` 为可空带默认值） |

## 5. 测试与验收

- JVM：`HostApiTest` 覆盖 `PATCH /display` 的正常 / 首选项 / 三态 / 403；`ContractTest` 覆盖 `DisplaySettingsDto` 与 `display.updated` 报文往返；`ClientMirrorTest` 覆盖 `display` 快照与事件应用。
- 仪表：沿用 `ClientSessionTest` 链路，补「改透明度 → 收到 `display.updated`」。
- 真机（用户执行）：手机删分类 / 删菜品两端同步；手机切换背景样式与拖透明度，平板展示页即时变化；手机上传相册背景图，平板铺满显示。

## 7. 实现位置与验证结果（M13，2026-10-07）

- 契约：`net/protocol/Contract.kt` 新增 `DisplaySettingsDto` / `DisplayPatchRequest`、`StateDto.display`、`EventType.DISPLAY_UPDATED`。
- 主机：`host/HostMessages.kt`（`MenuBackend.display/applyDisplay`、`saveBackgroundImage`）、`host/RepositoryMenuBackend.kt`、`host/HostApi.kt`（`PATCH /display` 路由与区间校验、`/images?kind=background` 分派规格）、`host/WsHub.kt`（`displayEvent`）、`host/HostServer.kt`（`DisplayUpdated` 事件 → 广播 `display.updated`；`/images` 解析 `kind`）、`data/MenuChange.kt`（新增 `DisplayUpdated`）、`data/MenuRepository.notifyDisplayChanged()`、`imaging/ImageStore.importBackgroundFromBytes`（长边 2048 / JPEG 85）。
- **展示设置可观察状态（关键修复）**：`data/DisplaySettingsState.kt` + `data/DisplaySettings.kt`。展示页原先直接读 `SettingsStore`（`SharedPreferences` 不可观察），手机改完设置主机虽已落盘并广播，**平板展示页却不重绘**；真机联调发现后改为「主机后端与管理页共用同一个 `DisplaySettingsState`」，展示页读它的 Compose 状态，改完立即重绘。`data/DisplaySpec.kt` 收敛透明度区间（`SettingsStore` / `HostApi` / 手机滑条共用，避免三处各写一套）。
- 客户端栈：`client/ClientMirror`（保存并应用 `display`，`display.updated` 不参与版本比较）、`client/ClientSession`（`updateDisplay` 提交即禁用 + 等广播对齐、`uploadBackgroundImage`）、`net/HostRestClient`（`updateDisplay`、`uploadImage(kind)`）。
- 手机界面：`ui/client/ClientMenuScreen`（分类 chip 右侧「×」、菜品行内「删除」，均走 `ConfirmDialog` 二次确认；长按入口保留）、`ui/client/ClientDisplayDialog.kt`（6 款内置样式色卡、相册上传 / 清除自定义背景图、蒙版与卡片透明度滑条、有货提示开关）、`ui/client/ClientSettingsDialog`（新增「展示设置」入口）、`ui/client/ClientApp`（上传与提交流程编排）。
- 配对深链接（顺带修复）：`ui/client/PairDeepLink.kt` + `MainActivity` + Manifest 的 `tanpai://pair` 与 `http(s)` intent-filter。此前二维码里的网址只是个提示，手机打不开；现在 `tanpai://pair?content=<二维码原文>`（或 `address` + `token`）能直接完成配对。
- 验证：JVM 单测 **169 项全通过**（新增 `HostApiTest` 展示设置三态 / 互斥 / 区间校验 2 项、`ClientMirrorTest` 快照与事件 1 项、`PairDeepLinkTest` 4 项）；`assembleDebug` 通过。
- 真机验证（小米 24122RKC7C 手机 + Teclast T10 平板，同一 Wi-Fi）：
  - 深链接配对成功，手机显示「在线 / 大金馄饨 / 12 道菜」；
  - 管理模式下列表出现分类「×」与菜品「删除」；误触「沽清」后用「恢复」回退，两端一致；
  - 手机「设置 → 展示设置」能读到平板当前值（喜庆红 / 25% / 15%）；
  - 对主机发 `PATCH /display`（等价于手机提交）后，平板主机日志出现 `已广播 display.updated（版本 42）给 1 个连接`，**平板展示页立即切换为竹青**、蒙版与「有货」提示同步变化，全程未重启应用 —— 即上面的可观察状态修复有效。
- **响应竞态修复**：`applyDisplay` 原先经 `Handler.post` 发布状态就返回，而 HTTP 管线在 IO 线程构建响应，导致 `PATCH /display` 的**响应体是旧值**（真机联调时表现为「发了 bamboo 却回 paper」，让人误以为补丁没生效，实际是下一帧才落库）。现改为 `commit()`：主线程直接赋值；后台线程同步等待主线程完成（最多 1 秒，超时自行赋值兜底），保证响应与落库一致。
- 与设计的偏差：展示设置写操作与菜单写操作一样受「允许手机编辑」开关约束（设计第 2.4 节即如此规定，实现一致）。

## 8. 未决事项

- 手机端是否也能改店名、微信二维码：当前不做（微信二维码为无损 PNG，规格与背景图不同）。
- 展示设置是否要单独一个开关（当前复用「允许手机编辑」）。
- 手机端上传自定义背景图的端到端真机验证（相册选图 → 上传 → 平板铺满）留待用户现场执行；主机端 `kind=background` 规格与校验已由代码路径覆盖。
