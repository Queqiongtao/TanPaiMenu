# 0002 局域网配对与同步

- 状态：已实现（M6、M7；M8 / M9 进行中，客户端侧 Phase 3）
- 对应阶段：Phase 2 / Phase 3
- 关联：`docs/design/0001-菜单数据模型与接口契约.md`、`docs/architecture.md`

## 1. 背景与目标

约定主机（平板）与客户端（手机）在同一局域网内的配对、鉴权、写命令与状态同步机制，保证「主机唯一写者」不被绕过，断线场景行为明确。

## 2. 角色与数据流

- 主机（平板）：持有 Room 与全局 `version`，所有写操作进入单写者队列串行执行。
- 客户端（手机）：不落库，内存镜像主机状态；读走 `/state` 与 WS，写走 REST。
- 数据流：客户端命令 → REST → 单写者队列 → 事务（业务写入 + `version` +1）→ WS 广播 → 各客户端应用。

## 3. 配对与鉴权

- 主机启动服务时生成随机 `pairToken`（32 字节随机数的十六进制），设置页可一键更换。
- 二维码内容：`http://<ip>:<port>/#pair=<token>`；`ip` 取当前 Wi-Fi 地址并实时刷新。
- 客户端请求带 `Authorization: Bearer <token>`；缺失、错误或旧 token 返回 401。
- 更换 token 后旧 token 立即失效，客户端下一次请求被拒并提示重新配对。
- 发现方式：`NsdManager` 自动发现、扫码、手动输入 IP，三者统一走同一配对流程。

## 4. 同步语义

- 写命令：客户端先乐观更新本地镜像，再用带 `requestId` 的请求提交；失败则回滚并提示 `error.message`。
- 广播：主机每次写事务提交后，向所有连接广播事件（格式见 `0001` 第 4 节）。
- 版本：客户端仅接受 `version` 大于本地版本的事件，乱序或过期事件丢弃。
- 断线：客户端显示离线条幅并进入只读，禁用全部编辑入口；恢复后重新 `/state` 全量对齐。

## 5. 安全与网络

- 传输为明文 HTTP + Bearer token；token 会出现在二维码与请求头中。
- 风险：同一网段内可被嗅探 / 重放。接受该风险的前提是使用摊位专用网络或平板热点。
- 后续如需加密：自签名 TLS + 证书指纹校验，属 Phase 4 可选增强（见 `docs/design/0005`）。

## 6. 主机实现设计

### 6.1 模块与职责

| 包 | 职责 | 交付 |
| --- | --- | --- |
| `net/protocol/` | 契约 DTO、ISO-8601 时间、实体 ↔ DTO 映射、事件类型常量（主机与客户端共用） | M6 |
| `data/` | Room 与仓储；写入口统一经单写者锁，提交后广播 `MenuChange` | M6 |
| `host/` | 服务生命周期、路由、鉴权、幂等缓存、连接管理、设备注册表 | M7 / M8 |

边界：`host` 只依赖 `data`、`net/protocol`；`net/protocol` 不依赖 Android 组件，可在 JVM 单测中直接验证。

### 6.2 单写者与事件流

- `MenuRepository` 内一把 `Mutex` 串行化全部写方法；`requestId` 幂等与跨方法顺序都由此保证。
- 事务提交后按提交顺序向 `events: SharedFlow<MenuChange>` 发出变更（携带新 `version`）。
- 事件只在提交成功后发出：回滚不发事件，保证「已广播的必然已落库」。
- 消费方：主机广播器（M7）向 WS 连接推送；本机 UI 仍走 Room `Flow`，不依赖事件流。

### 6.3 请求处理管线（M7）

`鉴权 → requestId 幂等查表 → 参数校验 → 单写者执行 → 事务提交 → 广播事件 → 返回响应`。

- 幂等缓存：内存 LRU 保留最近 200 条 `requestId → (状态码, 响应体)`；命中直接回放，不重复执行。
- 校验失败在进入单写者前返回，避免无效写占用队列。

### 6.4 设备注册表（M7）

- 新增 Room 表 `connected_device(id, name, role, lastSeen)`；WS 连接建立 / 断开时更新并广播 `device.joined` / `device.left`。
- `lastSeen` 超过 30s 视为离线；`/devices` 与设置页在线列表读该表。
- 库版本 1 → 2：`Migration(1, 2)` 仅新增表，不触碰既有数据。

### 6.5 前台服务与配对页（M8）

- `HostService`：前台服务持有服务器实例并保活；API 34 声明 `foregroundServiceType="dataSync"` 与对应权限。
- 配对页：显示 `IP:端口`、token（支持更换）、二维码 `http://<ip>:<port>/#pair=<token>`。
- 二维码用 `com.google.zxing:core` 生成位图（不引入 `zxing-android-embedded`，避免 Activity 依赖）。

### 6.6 新增依赖与设置项

- 依赖：`org.nanohttpd:nanohttpd:2.3.1`、`org.nanohttpd:nanohttpd-websocket:2.3.1`、`com.google.zxing:core:3.5.3`（M7 / M8 引入，构建需联网）。
- 设置（`SettingsStore`）：`pairToken`（首次启动生成）、`serverPort`（默认 8080）、`role`（主机 / 客户端，Phase 3 使用）。

## 7. 边界与失败场景

- 主机 IP 变化：二维码随 IP 刷新；客户端缓存上次 IP，重试失败后回到配对页。
- 主机息屏 / 被杀：前台服务保活；客户端断线转只读。
- 并发命令：单写者队列串行化，后到命令能看到前一条的结果。
- 服务端异常：返回 500 并写日志；客户端回滚乐观更新并提示。
- 时间不同步：不依赖设备时钟，仅用主机自增 `version` 判断新旧。

## 8. 测试与验收

- 两台设备同时改同一菜品，最终状态一致且无丢写。
- 错误 token 返回 401；更换 token 后旧客户端被踢出并提示重新配对。
- 拔网后客户端转只读，恢复后自动重连并回到可编辑。
- 幂等：断网重试同一 `requestId` 不产生重复扣减。
- 契约测试覆盖 `0001` 第 3.3 节全部接口的正常与错误路径（M9）。

## 9. 未决事项

## 10. 实现位置与验证结果（M6）

- 契约层 `net/protocol/`：`Contract.kt`（DTO、事件类型、错误码、PATCH 语义）、`Iso8601.kt`（UTC 毫秒格式化 / 解析，API 24 可用）、`Mapping.kt`（实体 ↔ DTO）。
- 单写者与事件：`data/MenuRepository.kt`（`writeMutex` 串行化，事务提交后按序发事件）、`data/MenuChange.kt`（DishUpdated / DishDeleted / CategoryUpdated / CategoryDeleted / FullReload）。
- 级联：删除分类先取启用菜品 id，事件 `CategoryDeleted.dishIds` 供对端逐条清理；回滚不发事件。
- 验证：JVM 单测 36 项通过（新增 `ContractTest` 12 项：ISO-8601、字段名、错误体、事件报文、PATCH / sell 请求解析）；真机 Teclast T10 / API 24 仪表测试 11 项通过（版本单调、提交顺序、失败不发事件、级联 id、10 并发卖出串行化）。

## 11. 实现位置与验证结果（M7）

- 服务与管线：`host/HostApi.kt`（鉴权 → 幂等 → 校验 → 单写者 → 响应）、`host/HostServer.kt`（NanoWSD 适配：`/api/v1/*`、`/ws`、multipart、端口顺延 8080→8082）、`host/WsHub.kt`（连接注册表 + `MenuChange` → 帧）、`host/RepositoryMenuBackend.kt`（落 `MenuRepository` / `ImageStore`）。
- 设备注册表：`connected_device` 表 + `data/db/DeviceDao.kt`；WS 连接建立 / 断开 upsert 并广播 `device.joined` / `device.left`；库 1 → 2 迁移见 `TpDatabase.MIGRATION_1_2`。
- 鉴权与配对信息：`Authorization: Bearer <pairToken>`；`SettingsStore.pairToken`（首次读取生成 32 字节随机十六进制）/ `serverPort`（默认 8080）；设置页「手机控制端」显示地址、配对码、二维码与「更换配对码」（断开现有连接）。
- 自启：服务在 `App.onCreate` 的 IO 协程内启动（前台服务保活属 M8），状态与配对信息写 `TpLog`。
- 细节与设计的偏差：请求体不依赖 NanoHTTPD `parseBody`（只解析 POST / PUT，且无 charset 时按 US-ASCII 解码会损坏中文），统一按 `Content-Length` 读原始字节并显式 UTF-8 解码；4401 关闭帧手工构造（库枚举无自定义码）；图片类型按魔数判定。详见 `0015` 第 6 节。
- 验证：JVM 新增 29 项（`HostApiTest` 18、`WsHubTest` 7、`HostInfoTest` 4）；仪表新增 10 项（`HostServerTest` 9 真实 HTTP / WS 往返、`TpDatabaseMigrationTest` 1）；平板 41 项全绿。真机 `curl` 走通 `/state`、`/devices`、中文分类的 `POST/PATCH/DELETE` 与幂等、错误码（401/400/404/409）；设置弹窗「手机控制端」显示状态、地址、配对码与二维码。
