# 0022 扫码配对

- 状态：已实现（M12，2026-10-07；本机 JVM 单测与构建通过，真机双机验收待用户执行）
- 对应阶段：Phase 5（M12）
- 关联：`docs/design/0019-手机客户端配对与只读浏览.md`、`docs/design/0018-角色选择与客户端运行形态.md`、`docs/design/0002-局域网配对与同步.md`、`docs/design/0015-主机服务接口实现.md`、`docs/architecture.md`

## 1. 背景与目标

手机客户端当前的接入方式是**手输**：在配对页填「平板地址 + 6 位一次性配对码 + 本机名称」。现场使用时摊主要先到平板「设置 → 手机控制端」点「显示配对码」，记下地址与 6 位数字，再回到手机上逐字输入——步骤多、易输错，是当前体验最差的一环。

平板侧其实**早就显示了配对二维码**（`HostInfo.qrContent`，M7 交付），内容为 `http://<ip>:<port>/#pair=<长期令牌>`，当初就是为扫码准备的；但客户端一直没实现扫码（`docs/design/0019` 第 7 节把它列为后续可扩展），二维码成了摆设。

目标：

1. 手机进入「手机客户端」形态且尚未配对时，**自动打开相机**，对准平板二维码即完成配对并进入菜单页，全程不需要输入任何字符。
2. **手动配对完整保留**，但默认收起在「手动配对」折叠项里；相机不可用（权限被拒、无摄像头、相机初始化失败）时自动展开，保证任何情况下都能配对上。
3. 主机侧**零协议改动**：不新增接口、不改二维码内容、不改 Room。

## 2. 方案设计（含取舍）

### 2.1 二维码内容沿用现状（关键决策）

二维码内容保持 `http://<ip>:<port>/#pair=<长期令牌>` 不变，其中：

| 组成 | 来源 | 说明 |
| --- | --- | --- |
| `ip` | `HostInfo.lanIpv4(context)` 实时读取 | 优先 `ConnectivityManager.activeNetwork` 链路地址，取不到退回 `WifiManager` |
| `port` | `HostServer.port` 实际绑定端口 | 默认 8080，被占用时顺延到 8082 |
| `token` | `SettingsStore.pairToken` | 32 字节随机数的十六进制（64 字符），首次读取时生成，只有「更换长期令牌」才会变 |

手机扫到后**直接落盘地址与 token**，跳过 `POST /pair`，随后复用既有 `ClientSession`（`GET /state` → `WS /ws`）。

取舍：

- **为什么不把 6 位一次性配对码放进二维码**：6 位码只有 5 分钟有效且一次性，二维码就得跟着轮换、加倒计时，过期或已消费后必须重新生成；平板还要新增「生成配对二维码」入口并在设置弹窗之外可唤出。收益只是让两条路径共用 `POST /pair`，代价却是显著增加的 UI 与状态复杂度，与本方案「扫一下就好」的目标相悖。
- **安全性**：二维码里的长期令牌本来就显示在平板设置弹窗里，而该弹窗需要 PIN 才能打开，因此扫码并没有扩大暴露面（能拍到二维码的人，已经能物理接触平板）。既有安全前提不变：摊位专用网络 + 明文 HTTP + Bearer 令牌（`docs/design/0002` 第 5 节）。
- **已知代价**：扫码路径不经过 `POST /pair`，因此平板上「最近配对：<设备名>」不会因扫码而更新（该字段只由 `PairCodeManager.consume` 写入）。在线设备列表不受影响——手机连上 WS 时会带自身设备名，平板照常显示。见第 6 节未决事项。

### 2.2 相机实现用 Camera2 + zxing core（关键决策）

| 方案 | 取舍 |
| --- | --- |
| Camera2 API + `com.google.zxing:core` 解码（**采用**） | **零新增依赖**（zxing core 3.5.3 已在类路径），APK 仅增几十 KB；解码只用 zxing 的 `PlanarYUVLuminanceSource` + `QRCodeReader`；自研相机生命周期约 250 行。API 24 兼容性最好。 |
| CameraX + zxing core | 相机代码更短、更现代，但要新增 `androidx.camera:camera-core/camera2/lifecycle` 并联网下载（本机 Gradle 缓存中无任何 camera 构件），APK 增大约 1–2MB。 |
| `zxing-android-embedded` | 自带 `CaptureActivity`，但要引 `appcompat`、与 Compose 混用，且与「不引入 Activity 依赖」的既有取舍（`docs/design/0002` 第 6.5 节）冲突。 |

采用 Camera2：只在手机形态使用，与平板主机形态（`docs/design/0018` 第 2.2 节）无关，不影响平板性能门禁。

### 2.3 交互设计

```text
手机客户端形态 · 未配对
┌──────────────────────────────┐
│ 连接平板                      │
│ 对准平板上的配对二维码        │
│   ┌────────────────────┐     │  ← 相机预览（TextureView）+ 取景框
│   │    取景框           │     │     实时解码，命中即配对
│   └────────────────────┘     │
│  扫描中… / 中文错误提示       │
│  ▸ 手动配对（地址 + 配对码）  │  ← 默认收起；点击展开原有表单
│  切换为平板主机               │
└──────────────────────────────┘
```

- 进入页面即申请相机权限并开预览；识别成功 → 落盘 → 进菜单页，无需点任何按钮。
- 非本系统二维码 / 解析失败：就地提示「请扫描平板上的配对二维码」并**继续扫描**，不退出相机。
- 权限被拒、无摄像头、相机打开失败：**自动展开**手动配对表单并给中文说明，功能不降级（手输路径与现状完全一致）。
- 手动配对区内保留「扫码配对」入口，用于用户主动切回相机。

### 2.4 分层与依赖

`ui` → `qrcode`（相机 + 解码）/ `client`（解析与落盘）；`qrcode` 不依赖 `client`，`net/PairQr` 是纯逻辑（不触达 Android），可在 JVM 单测直接验证。

## 3. 接口与数据模型变化

- **无网络协议变更**：不新增 REST / WS 端点，二维码内容与主机 `HostApi` / `HostServer` 完全不动。
- **无数据库变更**：不涉及 Room，无迁移。
- 新增 `net/PairQr.kt`：二维码文本 → `(主机地址, 令牌)` 的纯解析。接受两种写法：
  1. `http://<ip>:<port>/#pair=<token>`（主机当前输出；`#` 或 `?` 形式均可，令牌须为 ≥16 位十六进制）；
  2. `http://<ip>:<port>`（无令牌，报「二维码中没有配对令牌」）。
  其余内容一律判为无效：带 scheme 或形如主机名 / IPv4 但缺 `pair` 参数（如微信码 `https://weixin.qq.com/r/xxx`）报「二维码中没有配对令牌」；只含令牌、无地址或任意无关文本报「无法识别的内容」。仿冒内容（如 `http://evil.com/#pair=<token>`）不做域名白名单，但地址一律过 `HostAddress.normalize`，非 IPv4 / 主机名的畸形内容直接判为无效。
- 新增 `client/PairingClient.pairByQr(content, deviceName)`：解析 → 落盘 `clientHostAddress` + `clientToken` → 返回 `PairOutcome`（复用既有中文错误提示），与手输路径共用落盘逻辑。
- 新增 `qrcode/QrDecoder.kt`（亮度数组 → zxing 解码）、`qrcode/QrScanController.kt`（Camera2 生命周期、帧节流、结果与错误回调）、`ui/client/QrScanView.kt`（预览 + 取景框 + 权限与降级编排）。
- 修改 `ui/client/ClientConnectScreen.kt`（扫码为主 + 手动配对折叠）、`ui/client/ClientApp.kt`（接线）、`res/values/strings.xml`（新增中文文案）、`app/build.gradle.kts`（`versionCode 2` / `versionName 0.2.0`，便于两台设备确认安装的是新包）。
- `AndroidManifest.xml` **无需改动**：`CAMERA` 权限与非必需 `uses-feature android:hardware.camera` 早在 Phase 1「传图（拍照）」时已声明。

## 4. 边界与失败场景

| 场景 | 行为 |
| --- | --- |
| 相机权限被拒 / 无摄像头 / 相机初始化失败 | 自动展开手动配对表单 + 中文提示，配对能力不受影响 |
| 扫到微信码、商品码等非本系统内容 | 提示「请扫描平板上的配对二维码」，继续扫描 |
| 扫到本系统二维码但令牌缺失 / 地址非法 | 提示「二维码中没有配对令牌」/「二维码中的平板地址无效」，继续扫描 |
| 扫到只含令牌（无地址）或任意无关文本 | 提示「无法识别的内容，请扫描平板上的配对二维码」，继续扫描 |
| 二维码是几天前的截图 | 面板显示的地址过期 → 落盘后走既有「无法连接平板，请确认手机与平板在同一 Wi-Fi」退避重连提示，用户可重新扫码 |
| 平板换过长期令牌 | 落盘的 token 失效 → 既有 401 / WS 4401 路径提示「配对已失效，请重新配对」 |
| 平板未开「手机控制端」 | 平板上没有二维码；手机扫码后连不上，提示同上（与手输一致） |
| 前后台切换 / 息屏 / 弹窗 | 相机会话按生命周期释放与重建，不在后台占摄像头 |
| 已配对状态下重开 App | 直接进菜单页，不弹相机（保持现状） |
| 扫描期间重复命中 | 配对请求期间暂停取帧回调，不重复发请求 |

## 5. 测试与验收

- **JVM 单测**（本次补齐）：`PairQrTest` 覆盖现有二维码格式、`?pair=` 写法、裸地址、纯令牌、缺令牌、非法地址、畸形内容、含空白与换行、大写下十六进制等分支。
- **不回归**：主机侧与手输配对路径不改动语义，既有 JVM 单测（139 项）与平板仪表测试（56 项）应保持全绿。
- **构建**：`gradlew assembleDebug` 通过并产出新 APK。
- **真机**（由用户执行，两机安装新包）：
  1. 手机首启选「手机客户端」→ 相机自动打开 → 扫平板二维码（平板需已开手机控制端）→ 1 秒内进入菜单页并显示 12 道菜。
  2. 平板改价 → 手机 1 秒内跟随，证明扫码落盘的 token 可正常读写。
  3. 拒绝相机权限 → 手动配对表单自动展开，手输地址 + 6 位配对码仍可配对成功。
  4. 扫非本系统二维码 → 有中文提示且相机不退出。
  5. 手机「重新配对」→ 再次扫码可用。
  6. 平板换 Wi-Fi 导致 IP 变化 → 重新扫码后恢复（验证二维码随 IP 变化）。

## 6. 未决事项

- 扫码是否也更新平板上的「最近配对：<设备名>」：需要主机侧配合（二维码追加设备名参数，或新增凭 token 登记设备的接口），当前不做。用户如需要再单独立项。
- 手机端 NSD / mDNS 自动发现（平板换 IP 后自动找回）：仍未实现，见 `docs/design/0019` 第 7 节。
- 二维码安全模型升级（一次性配对窗口 / 有效期）：当前沿用长期令牌，理由见第 2.1 节。

## 7. 实现位置与验证结果（M12，2026-10-07）

- 解析：`net/PairQr.kt`（`PairQr.parse` → `Result.Parsed(hostAddress, token)` / `Result.Failed(reason)`；接受 `#pair=` 与 `?pair=`，地址经 `HostAddress.normalize` 校验，令牌要求 ≥16 位十六进制）。
- 落盘：`client/PairingClient.pairByQr`（仅解析 + 写 `clientHostAddress` / `clientToken`，不发起网络请求）；同时把 `pair()` 的设备名回退改为「沿用已保存名称」，不再覆盖用户改过的名字。
- 相机与解码：`qrcode/QrDecoder.kt`（zxing `PlanarYUVLuminanceSource` + `HybridBinarizer` + `MultiFormatReader`，仅 `QR_CODE`）、`qrcode/QrScanController.kt`（Camera2：后置摄像头选择、预览尺寸按相机能力选 640×480–1920×1080 中最接近 1280×960 的一档、`ImageReader` 取 `YUV_420_888` 的 Y 平面并逐行去除 stride 填充、1.5 秒周期自动对焦、命中闸门保证同一二维码只回调一次、`stop()` 幂等并释放相机与线程）。
- 取景显示（真机调试后定稿）：取景窗口固定 **16:9**、高度上限 260dp（竖屏不被拉成长条，横屏不占满整屏）；纹理用等比 **center-crop** 铺满窗口，公式为 `scale = max(视宽/缓冲宽, 视高/缓冲高)` 后再在缓冲坐标里居中。踩过的两个坑：① 早期把宽高按显示方向互换，造成**非等比缩放**（正方形被拉长）；② 把比例写成倒数，在「16:9 窗口 + 4:3 相机流」时整块变黑。预览尺寸也不再按控件尺寸挑（那会与窗口尺寸形成循环依赖，实测选到过 352×288）。
- 界面：`ui/client/QrScanView.kt`（`CameraScanner`：相机权限申请、`QrScanController` 与 `TextureView` 绑定、取景框与错误提示、相机不可用时回调外层）、`ui/client/ClientConnectScreen.kt`（默认相机为主，「手动配对（地址 + 配对码）」默认收起，手动表单内保留「改用扫码配对」入口）。
- 资源与版本：`res/values/strings.xml` 新增 7 条中文文案；`app/build.gradle.kts` 升为 `versionCode 2` / `versionName 0.2.0`（便于两台设备确认装的是新包）。`AndroidManifest.xml` 未改动（`CAMERA` 权限与非必需 `uses-feature` 早已声明）。
- 验证：JVM 单测 **162 项全通过**（新增 `net/PairQrTest` 12 项：主机二维码原文、`?pair=` 写法与大写令牌、前后空白与换行、附加 fragment 参数、缺端口补默认端口、缺令牌、空令牌、端口越界、端口非数字、外部二维码、纯令牌、无关文本、过短令牌、非十六进制令牌）；`assembleDebug` 构建通过，产出 `out/app/outputs/apk/debug/app-debug.apk`（22,165,998 字节，Phase 4 基线为 21,987,981 字节，零新增依赖）。
- 真机验证（小米 24122RKC7C / Android 14，`adb` 装包实测）：
  - 相机权限已授予时进入配对页即打开后置摄像头（日志 `Camera 0: Opened. Client: com.tanpai.menu`），选到预览 1280×960；
  - 竖屏取景窗口为 944×531（16:9），画面等比铺满、无拉伸；
  - 横屏取景窗口为 2143×1205（16:9），画面等比铺满、无拉伸，且不再占满整屏；
  - 帧流稳定（30fps）且亮度正常（平均 Y 100+），排除了「预览黑」是取流问题。
  - 未覆盖：完整「扫平板二维码 → 配对成功」链路需两台设备对着扫码，留待用户现场验收。
- 与设计的偏差：无（主机侧与协议确实未改动）。
- 已知限制：扫码路径不写 `pairedDeviceName`，平板「最近配对：<设备名>」只在手输配对后更新（见第 6 节）。
- 环境说明（与产品无关）：本机 DSH 沙箱当前拦截 `app/build` 路径下的写入，`AAPT` 无法产出产物；本次构建把输出目录临时重定向到 `out/`（命令行 `--project-cache-dir` + 临时 `buildDir` 覆盖）后通过。用户在本机自行构建时用常规 `scripts\build-and-install.bat` 即可。
